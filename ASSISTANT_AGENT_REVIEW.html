The short version

What the agent is, what it is worth, and where its ceiling comes from.

Assistant Projet is a supervised tool-using assistant, not an autonomous agent. That is a strength before it is a limitation: the hard part of putting a model inside a CRM is not making it clever, it is making it safe to leave switched on. This codebase has solved the hard part. The ceiling now comes from the loop around the model, not from the model itself.

What is genuinely strong

Scope is structural. The active project is resolved server-side and every query derives its where from the envelope, not from model arguments.

Irreversible work needs a human. Confirm tools stop the loop; the card is rebuilt from the database, and the stored action is re-read and re-validated on execution.

Secrets bypass the model. Password-shaped keys are stripped from every payload; a revealed password travels server → UI only.

Every write leaves a trace. Actor, arguments, project, outcome and cost are recorded.

What caps it

No evidence memory. Tool results are discarded after the turn; the model is instructed to re-fetch facts it already had.

No verification. Nothing checks that a number in the answer came from a tool result.

No plan. Five iterations, one tool at a time, no explicit decomposition for multi-part questions.

No behavioural evals. The test suite protects permissions, not answer quality, prompt changes or regressions.

No resilience. No timeout, retry, fallback provider or streaming on the provider call.

Five findings

  1. The power is in the harness, not the model. Frontier agents feel different because they plan, manage context, act in an environment that answers back, verify with real checks, and remember across sessions. This agent does one turn of tool use at a time.
  2. Trust is this agent's moat, and it is real. Most product agents enforce scope in a prompt. This one enforces it in a context object, a pure guard, and a stored pending action. That is harder to build than a longer loop.
  3. Evidence is the missing middle. Without a persisted ledger, the agent cannot cite, cannot stay consistent across follow-ups, and cannot prove an answer. Everything else — verification, memory, evals — depends on this one addition.
  4. The default model is a cost decision that became an architecture decision. One cheap model does planning, tool selection, writing and judgement; there is no routing, fallback or escalation.
  5. The documented design has drifted from the code. The architecture doc names Mistral, 6 tool calls and 4 round-trips; the implementation runs OpenAI, 8 calls and 5 iterations. The code is the truth; the doc is now a risk.

Recommendation

Do not chase generality. Make this a bounded, evidence-first agent: every factual answer carries evidence ids, every complex request gets a small explicit plan, every answer passes a groundedness check, and context is compiled to a budget instead of accumulated. Keep the envelope, the guard and the click exactly as they are.

Why this is above the market, not behind it

Most product agents put scope in the system prompt and hope. Here the binding is part of the request object, every tool derives its query from it, the guard cannot fail open because it does no I/O, the confirmation card is rebuilt from the database, and the execution route refuses a second click. Those four decisions are why this assistant can hold client data at all.

Documentation drift — a real operational risk

AI_ASSISTANT_ARCHITECTURE.md describes “Mistral Large”, a maximum of 6 tool calls and 4 model round-trips. The code runs gpt-4o-mini, caps 8 calls and 5 round-trips, and the doc's own header still says “Nothing below is implemented yet except where marked [built]”. Anyone tuning the assistant from the document will tune the wrong system.

02 · MechanicsOne turn, step by step
02

What happens between a question and an answer

The loop is a clean ReAct pattern with hard budgets and one human interrupt.

The turn

  1. Load. The route reads the conversation from the database and refuses a conversation the caller does not own.
  2. Resolve. Context is rebuilt: user, role, permissions, bound client and mission, date, write budget.
  3. Compose. A 73-line French system prompt plus an 8-rule tool-usage prompt. No retrieved examples, no project brief, no few-shot tool traces.
  4. Call. The model sees all accessible tool schemas and picks zero or more. Reads and safe-writes run immediately, sequentially.
  5. Interrupt. A confirm tool stops the turn. Its card is built from a database lookup, not from the model's description.
  6. Persist. User and assistant messages are written in one transaction, with the trace, cost and pending action.

The envelope the model cannot argue with

role, isActive, permissions[] project: { clientId, missionId } resolvedAt, autoWriteBudget, conversationId AssistantContext · lib/ai/tools/types.ts:50–72

Every project tool derives its where clause from this object. If the model passes another client's id, the tool ignores it or refuses. The isolation is a property of the request, not a promise in the prompt.

Four design decisions worth keeping

Failures are data

A denied or invalid tool call goes back to the model as a structured error with a note telling it not to invent data. The loop continues; the manager gets an explanation, not a stack trace.

Risk is declared, not judged

Each tool carries risk: read | safe_write | confirm. The loop's behaviour follows the declaration, so a new sensitive tool cannot accidentally run itself.

Secrets have a separate path

Credential-shaped keys are stripped recursively; a revealed password goes server → card, is shown once, and is never written into the transcript.

Replay is treated as an attack

The execute route reads the pending action from the stored message, rejects anything not pending with 409, and re-checks that the tool is confirm-class. A stale tab cannot send twice.

Cards are facts, not summaries

The onboarding card resolves recipients, exclusions and the exact warning from the database. The model proposes the action; the UI shows what will actually happen.

Cost is measured per turn

Prompt, completion and total tokens are accumulated across iterations and priced into euros, then stored with the trace. This is the raw material for a real budget policy.

The one sentence that explains the ceiling

The tool-usage prompt tells the model: “les résultats d'outils des tours précédents ne sont PAS dans ton contexte, seul le texte de tes réponses l'est” — so the agent re-fetches facts it already retrieved. That is a deliberate workaround for not persisting evidence, and it is the single highest-leverage thing to change.

Not present in the request path: streaming, cancellation, provider timeout, retry, fallback model, parallel read execution, response schema for answers, citation of tool results, and any post-generation check. The UI waits for the full JSON response.

03 · Frontier agentsWhere the power comes from
03

Eight primitives, one of which is the model

Model quality sets the ceiling. The harness decides how much of that ceiling is reached.

The felt difference between a demo agent and a powerful one is rarely the model alone. It is a stack of eight capabilities that reinforce each other: a goal held across time, context managed instead of accumulated, tools that behave like an interface, an environment that answers back, verification against reality, memory outside the window, and measurement that catches regressions.

01 / MODEL

Reasoning that holds a goal

Long context, reliable tool selection, the ability to notice its own mistake and change approach. Necessary, not sufficient.

02 / HORIZON

A loop that can keep going

Plan → act → observe → revise until an exit condition is met. State lives outside the prompt, so a long task survives a context reset.

03 / CONTEXT

Compiled, not accumulated

Select the relevant tools and evidence, compress history, isolate sub-tasks, retrieve just in time. Context is a budget, not a transcript.

04 / TOOLS

An interface, not a dump

Few, orthogonal, typed tools with examples, machine-readable errors, idempotency and a clear cost. The tool list is part of the prompt.

05 / ENVIRONMENT

Something that answers back

Files, shell, browser, APIs, tests. The agent gets ground truth from execution instead of grading its own homework.

06 / VERIFY

“Done” is checked

Run the test, open the page, compare the number to the source, ask a second reader. The verification step is part of the loop, not a hope.

07 / MEMORY

State that outlives the chat

Notes, project facts, decisions, prior attempts. Retrieval when needed, not a 20-message window replayed forever.

08 / EVALS

Measurement as a feature

Golden tasks, expected tool calls, groundedness checks, cost and latency budgets, trace review. Improvement without regression.

The four loops frontier agents close

Plan loop. The task is decomposed before tools are called, and the plan is revised when a step fails. This is what makes a ten-part request feel handled rather than truncated.

Context loop. The harness decides what the model sees at each step: which tools, which evidence, which summary. A bigger window is not a strategy; compaction is.

Reality loop. Environment feedback — a compiler error, a failing test, a rendered page — tells the agent whether its action worked. Without it, the model's confidence is the only signal.

Improvement loop. Traces become eval cases; eval cases gate prompt and model changes. The product gets better because failure is measurable.

Why “just use a better model” is not the answer

A stronger model inside this harness would write better sentences, choose tools more reliably, and recover from a bad argument more often. It would still forget the evidence after one turn, still stop at five iterations, still have no way to prove a number, and still be untestable beyond permissions.

The reverse is also true: the best harness in the world cannot make a weak model reason about a ambiguous request. The two multiply. Today this product has invested almost entirely in the multiplier that protects the business — and almost nothing in the multiplier that makes the agent capable.

Reading note

This section describes an architectural pattern, not the internals of any vendor's product. No claim is made about a specific unreleased model. A model named “GPT Astra” could not be verified, so the comparison is against the Claude/GPT-class agent pattern as it appears in shipped agent products.

04 · ComparisonTwo kinds of power
04

Reach versus trust

They are not levels of the same thing. They are different bets about what an agent is for.

Power A

Reach

The general agent: an open-ended harness that can act on a computer, recover from failure, and keep a goal alive across hundreds of steps.

  • Wins on novel, multi-step, ambiguous work
  • Improves through its own failures
  • Trusts the environment to tell it the truth
  • Costs latency and tokens; hard to bound
  • Dangerous when pointed at irreversible actions
Power B

Trust

The product agent: a narrow, typed, audited surface that knows one domain and cannot leave it.

  • Wins on permissioned data and real actions
  • Deterministic where it matters: scope, secrets, sends
  • Fits the workflow instead of replacing it
  • Cheap to run, easy to audit
  • Cannot recover from a failed step on its own

The asymmetry that matters

A general agent can fail and try again. This agent can fail and must ask the manager. That is the correct trade for sending an email or revealing a password. It is the wrong trade for reading data: a failed read should trigger a different query, not a question to the user. The design currently applies one caution level to both.

Copy from the frontier

Explicit plans for complex requests · an evidence ledger with citations · a context compiler with a token budget · a groundedness verifier · golden evals in CI · project memory · parallel reads · streaming · model routing and fallback.

Do not copy

Open-ended autonomy · shell or filesystem access · cross-project memory (it breaks the one-project rule) · autonomous external sends · self-graded success · unbounded loops.

Three requests, three different outcomes

“What is at risk this week?”

Works. One agency tool returns flagged clients with reasons. The model narrates. No verification, but the data is one call deep.

Outcome: useful in seconds.

“Compare Q2 and Q3, per SDR, then explain the drop.”

Struggles. Two periods × per-SDR detail can consume the 8-call budget before synthesis; no plan allocates it. The answer may stop at the first table.

Outcome: partial or a request to reformulate.

“Draft the access email and send it to the three new commerciaux.”

Works well. Draft is a safe write; send is a confirm card rebuilt from the database with recipients and exclusions; the click is the authorisation.

Outcome: exactly the flow the product was built for.

What the pattern says

The assistant is strongest when the task is one tool deep and one action wide. It is weakest when the task needs synthesis across several sources, or a second attempt after a failed lookup. Those are exactly the tasks a manager calls “analysis”.

A layout that lets each concern fail alone

The current framework is good; it needs seams, not a rewrite.

// target layout — existing modules move, new ones are added lib/ai/ agent/ envelope · planner · runtime · models context/ compiler · budget · tool-groups tools/ registry · guard · executor · definitions evidence/ ledger · citation verify/ extract · checks · verifier memory/ summary · facts actions/ broker observability/ trace · metrics evals/agent/ golden/*.json · run.ts · judge.ts

New: planner, compiler, evidence, verification, memory, action broker. Kept as-is: registry, guard, executor, all 34 definitions. The full tree and every interface are in the companion blueprint.

The five types that carry the design

type PlanStep = { id: string; intent: string tool?: string; args?: unknown dependsOn?: string[] } type EvidenceItem = { id: string; tool: string argsHash: string; at: string summary: string payloadRef: string // never the model } type AgentAnswer = { text: string citations: string[] // evidence ids plan: PlanStep[] action?: PendingAction verified: boolean } Proposed contracts — companion blueprint has the full definitions

The invariant to enforce in code

No factual sentence without an evidence id. The verifier extracts numbers, dates and named entities from the draft and checks each one against the evidence attached to the turn. A number that cannot be traced is either removed or the answer is regenerated with the evidence made explicit.

This is deliberately narrower than “the model must be right”. It is a mechanical property: every figure in the answer appears in a tool result the manager could open. That is what makes the answer auditable, and it is the one property this CRM can offer that a general agent cannot.

Three request lifecycles

A · Simple read

Classify → compiler picks one tool group → 1–3 parallel reads → ledger append → verifier → answer with citations.

Same latency as today, plus one cheap check. The planner is skipped.

B · Synthesis

Classify → plan 3–6 steps → batch independent reads → compress evidence → draft → verify each figure → answer or repair once.

New capability. Budget is spent by the plan, not by improvisation.

C · Action

Propose → broker creates a pending action with idempotency key → card from DB → click → execute in a transaction → audit → undo token.

Today's flow, hardened. Duplicate and stale clicks already blocked; add expiry and undo.

08 · RoadmapOrder of work
08

Five phases, each with a testable exit

Sequence by dependency, not by ambition. Evidence comes before verification; verification before memory.

Phase 0 removes the operational sharp edges. Phase 1 adds the ledger every later phase reads from. Phase 2 makes the agent economical and able to plan. Phase 3 makes it check itself and makes quality measurable. Phase 4 gives it continuity and hardens the action path. Effort is indicative: S is a focused change, M is a module, L is a programme of work.

P0
S

Stop the sharp edges

Add an abort signal and timeout to the provider call, one retry with backoff on 429/5xx, an env-driven model and a fallback model, and streaming in the panel. Align the architecture document with the code.

Exit: no request can hang indefinitely; a transient provider failure produces a typed error or a retry; the manager sees tokens before the turn ends; the doc names the real model, caps and provider.

P1
M

Evidence ledger and citations

Wrap every tool result in an EvidenceItem. Store the digest with the run; put a compact digest, not the payload, into the next turn's context. Return citations with the answer and show them in the panel's source tray.

Exit: every figure in an answer maps to an evidence id; a follow-up reuses the prior evidence instead of re-querying identical data; the manager can open the source of any claim.

P2
M

Context compiler and planner

Introduce tool groups and a token budget per section. Add a planner for requests that need more than one source, with 1–6 typed steps, dependency ordering and parallel reads. Keep the single-tool path untouched.

Exit: system, tools, history and evidence fit a declared budget; only the relevant tool group is advertised; multi-part questions produce a plan that is visible in the trace and completes or fails explicitly.

P3
L

Verifier and behavioural evals

Extract numbers, dates and entities from the draft; require each to appear in the turn's evidence. Add scope and card checks. Build the 40-case golden set and run it in CI on every prompt, tool or model change.

Exit: an unsupported number blocks or repairs the answer before it is stored; a prompt change that regresses a golden case fails the build; groundedness and re-fetch rate are visible per run.

P4
M

Memory and action broker

Add a rolling project summary and durable facts with source evidence and expiry. Move confirm actions to an outbox with idempotency keys, expiry and an undo token for safe writes.

Exit: a new thread knows the project's agreed facts and decisions; a duplicated or expired click cannot execute; a safe write can be undone from the trace.

Sequencing rule

Do P0 and P1 before touching the model. A stronger model on top of a harness that forgets its evidence produces more convincing unverifiable answers — the worst possible outcome for a CRM that sends client email.

Why evidence first

Verification reads the ledger. Memory writes to the ledger. Citations point at the ledger. Evals assert against the ledger. Each later feature is a consumer of this one table; building any of them first means building a second source of truth.

Why not a rewrite

The registry, guard, executor, risk tiers, confirmation cards and audit are the expensive, correct parts. They stay. The change is additive: new modules around the loop, one field on the tool result, one stage after generation.

The prompt is a product surface, not a string

Today the system prompt is 73 lines of role, domain, method and tone, plus 8 usage rules. It is well written, but it carries no examples, no project brief, no schema for the answer and no instruction to cite. Three additions matter more than length: two worked tool traces (one read, one confirm), the expected answer shape (figures with periods, sources, explicit unknowns), and a rule for what to do when a verification fails — repair once with the evidence, then say plainly what could not be confirmed.

Measure the agent like a product, not a demo

A small eval set reviewed weekly beats a large one reviewed never.

The proposed eval set — 40 cases

CategoryCasesAsserts
Single-fact lookup8Right tool, exact figure, period stated.
Multi-source synthesis8Plan covers all parts; every figure traced.
Follow-up and coreference6Reuses evidence; no invented id.
Action proposal8Confirm card, correct recipients, no execution.
Scope and refusal6Refuses cross-project, explains, offers switch.
Injection and secrecy4No secret in output; injected text not obeyed.

Each case stores input, required tools, forbidden tools, required facts and a short rubric. Rule checks run first; a model judge is used only for tone or explanation quality. Counts are a proposal, not a measurement.

Six metrics worth a dashboard

MetricDefinition
Grounded answer rateShare of answers whose figures all map to evidence.
Tool success rateSuccessful executions ÷ attempts, by tool.
Re-fetch rateIdentical query repeated within a conversation.
Plan completionSteps completed ÷ steps planned, per run.
Cost per resolved questionTotal tokens priced in euros, including retries.
Confirmation acceptanceConfirmed ÷ proposed actions; a falling rate is a signal.

Latency should be reported as median and p95, never as an average alone. Cost should be split by phase — plan, tools, draft, verify — or it cannot be optimised.

Weekly trace review — 20 runs, 30 minutes

  1. Sample 20 runs across managers and projects, including refusals.
  2. Label each failure: wrong tool, right tool wrong args, right data wrong reasoning, unsupported claim, correct refusal, latency.
  3. Promote every new failure shape into a golden case.
  4. Review cost and p95 for the week; investigate any step change.

Model policy

Planner and verifier run on the strongest available model; extraction and formatting run on the cheap one; drafting runs on a mid tier. Writes never depend on model confidence — only on a validated schema and a human click. Every model id is configuration, never a literal in a route.

The one-line test for every new capability

Can the agent do it with a read tool, inside the envelope, without a new permission? If not, it is a product decision, not a prompt change.

Method and limits

This is a static review of the repository: the assistant routes, tool framework, definitions, prompt, UI components, package scripts and the architecture document. The application was not run, no database was queried, and no provider call was made, so runtime behaviour and current data quality are not measured here.

The frontier-agent comparison is an architectural analysis of shipped agent patterns, not a description of any vendor's internals and not a benchmark. No model named “GPT Astra” could be verified; the comparison is deliberately framed as Claude/GPT-class.

Counts (34 / 23 / 3 / 8) come from the registry and its comments. Proposed eval counts, target metrics and effort labels are proposals for approval, not findings.

The decision this review asks for

Approve P0 and P1. They are small, additive, and they make every later improvement measurable. P0 removes the failure modes a manager feels today — a hanging panel, a provider hiccup, a blank wait. P1 creates the evidence layer that turns a fluent answer into an auditable one.

Defer the planner and the stronger models until the ledger exists. Capability added before proof is capability you cannot trust.
